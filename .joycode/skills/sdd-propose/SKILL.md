# SDD Propose - 规格驱动开发提案

基于规格驱动开发（SDD）思想的提案技能，帮助用户通过结构化流程创建变更提案。

## 使用场景

- 用户想要开始一个新的功能开发
- 用户需要一个结构化的开发计划
- 用户描述了需要构建或修复的内容
- 用户输入 `sdd-propose` 或提到"创建提案"、"规格提案"、"SDD提案"

## 工件存放路径

所有 SDD 工件统一存放在 `dev_logs/<change-name>/` 目录下：
```
dev_logs/
  └── <change-name>/
      ├── proposal.md    (做什么 & 为什么)
      ├── design.md      (怎么做)
      └── tasks.md       (实现步骤)
```

## 工作流程

### 输入

用户需提供变更名称（kebab-case）或对要构建内容的描述。

### 步骤

1. **确认用户意图**

   如果没有提供明确的输入，询问用户：
   > "你想要开发什么功能？请描述你想构建或修复的内容。"

   从描述中推导出 kebab-case 名称（如"添加用户认证" → `add-user-auth`）。

   **重要**: 必须理解用户想要构建的内容后才能继续。

2. **加载项目上下文**

   读取以下文件获取项目知识（按需）：
   - `ai-context/project-context/index.md` — 技术栈、编码规范、已有工具类
   - `ai-context/biz-context/index.md` — 已有领域实现、避免重复

3. **创建变更目录**

   在 `dev_logs/<name>/` 下创建变更目录。

4. **按顺序创建工件**

   依次创建以下工件：

   a. **proposal.md** - 提案文档
      - 概述：做什么、为什么
      - 目标：具体要实现的能力列表
      - 非目标：明确范围边界
      - 技术约束
      - 影响范围
      - 成功标准

   b. **design.md** - 设计文档
      - 技术选型
      - 类/模块结构设计
      - 方法行为规范
      - 设计决策及原因
      - 线程安全/性能考量

   c. **tasks.md** - 任务清单
      - 按依赖顺序的实现步骤
      - 每个任务使用 `- [ ]` 标记（未完成）
      - 单个任务粒度控制在 2 小时内
      - 包含明确的交付物描述

4. **显示最终状态**

   总结已创建的工件列表。

### 输出

完成所有工件后，总结：
- 变更名称和位置（`dev_logs/<name>/`）
- 已创建的工件列表及简要描述
- 就绪状态："所有工件已创建！准备好实现。"
- 提示："使用 `/sdd-apply` 开始实现任务。"

## 护栏规则

- 创建 proposal → design → tasks 三个完整工件
- 创建 design 前先读取 proposal 作为上下文
- 创建 tasks 前先读取 proposal 和 design 作为上下文
- 如果上下文严重不清楚，询问用户
- 如果 `dev_logs/<name>/` 已存在，询问用户是继续还是覆盖
- 写入每个工件文件后验证其存在
