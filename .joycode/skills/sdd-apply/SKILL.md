# SDD Apply - 规格驱动开发实现

按照 `dev_logs/<change-name>/` 下的 proposal/design/tasks 工件规格，逐步执行代码实现。

## 使用场景

- 用户已完成提案，准备开始实现
- 用户想继续进行中的实现
- 用户输入 `sdd-apply` 或提到"开始实现"、"执行任务"、"SDD实现"

## 工件读取路径

从 `dev_logs/<change-name>/` 读取上下文：
```
dev_logs/
  └── <change-name>/
      ├── proposal.md
      ├── design.md
      └── tasks.md
```

## 工作流程

### 输入

可选指定变更名称。如果省略，从对话上下文推断。

### 步骤

1. **选择变更**

   如果提供了名称，使用它。否则：
   - 从对话上下文推断用户提到的变更
   - 扫描 `dev_logs/` 下的目录，如果只有一个活跃变更，自动选择
   - 如果模糊不清，列出 `dev_logs/` 下所有变更目录让用户选择

   始终宣布："使用变更: <name>"。

2. **加载项目上下文**

   读取 `ai-context/project-context/index.md` 获取：
   - 编码规范、代码模板（确保生成的代码风格一致）
   - 禁止事项（避免踩坑）
   - 已有工具类索引（避免重复造轮子）

3. **读取变更上下文文件**

   读取 `dev_logs/<name>/` 下所有工件：
   - `proposal.md` - 理解做什么、为什么
   - `design.md` - 理解怎么做、设计决策
   - `tasks.md` - 获取任务清单和进度

3. **显示当前进度**

   展示：
   - 进度："N/M 任务完成"
   - 剩余任务概览

4. **实现任务（循环直到完成或阻塞）**

   对每个 `- [ ]` 待处理任务：
   - 显示正在处理的任务
   - 进行所需的代码变更
   - 保持变更最小化且聚焦
   - 在 `dev_logs/<name>/tasks.md` 中标记完成：`- [ ]` → `- [x]`
   - 继续下一个任务

   **暂停条件：**
   - 任务不清晰 → 询问澄清
   - 实现中发现设计问题 → 建议更新 design.md
   - 遇到错误或阻塞 → 报告并等待指导
   - 用户中断

5. **完成或暂停时显示状态**

   展示：
   - 本次会话完成的任务
   - 总体进度："N/M 任务完成"
   - 如果全部完成：建议归档
   - 如果暂停：解释原因并等待指导

### 输出格式

**实现中：**
```
## 正在实现: <change-name>

处理任务 3/7: <任务描述>
[...实现中...]
✓ 任务完成
```

**完成时：**
```
## 实现完成

**变更:** <change-name>
**进度:** 7/7 任务完成 ✓

所有任务完成！可以使用 `/sdd-archive` 归档此变更。
```

## 护栏规则

- 持续处理任务直到完成或阻塞
- 开始前始终读取 `dev_logs/<name>/` 下的上下文文件
- 如果任务模糊，暂停并在实现前询问
- 如果实现暴露问题，暂停并建议更新 design.md
- 保持代码变更最小化且限定在每个任务范围内
- 完成每个任务后立即在 tasks.md 中更新复选框
- 遇到错误、阻塞或不清晰的需求时暂停 - 不要猜测

## 流式工作流集成

- **随时可调用**: 部分实现后可继续、可与 `/sdd-explore` 交替使用
- **允许工件更新**: 如果实现暴露设计问题，可更新 `dev_logs/<name>/design.md`
